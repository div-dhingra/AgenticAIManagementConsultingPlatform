AGENT INTERNAL DESIGN
Use LangGraph StateGraph with explicit state, bounded transitions, and a compiled
graph. Keep framework objects private; return ConsultResponse at the boundary.
Suggested state: request, request_id, selected_domains, per-domain subquestions,
retrieved_chunks_by_id, specialist_results, candidate_rankings, validation_issues,
clarification_questions, final_result, trace, warnings, remaining_call_budget.

Manager routing produces validated JSON with selected domain labels and task-level
subquestions. A single question can select multiple domains. A purely out-of-scope
request gets no invented specialist answer; return insufficient_evidence, domains
[], and a scope explanation. Ambiguous intent gets needs_clarification.
Use question plus context. Add deterministic validation of the router output.
Keep a simple keyword-based baseline for evaluation; disclose it if used.

Graph shape:
  validate_input -> route -> dispatch selected specialists -> validate evidence
  -> optional targeted second pass -> synthesize -> final contract validation
Selected specialists can run concurrently, with isolated result objects merged
by domain; do not let concurrent nodes overwrite a shared evidence list. A simple
async dispatch node using gather is acceptable if documented. Four domains must
be separately configured runners/nodes, not a single prompt pretending it used
specialists. A specialist can choose a refined retrieval query or clarification.

Bound execution: at most two retrieval rounds per selected specialist; at most
one manager-directed follow-up for the request; follow-up stays inside that
specialist's two-round budget. At most 12 total LLM calls, including one bounded
JSON-repair attempt if needed, and a 90-second overall deadline. Stop early when
evidence is adequate. Return honest partial results when a domain is unavailable;
map complete infrastructure failure to the shared exception types.

SPECIALIST POLICIES
Technology: Cisco first, then other indexed technology sources. Retrieve exact
model/spec evidence. Separate symptoms from confirmed faults. A datasheet can
support option compatibility, but cannot establish a component has failed. Ask
for model/logs/diagnostics before unsupported procurement recommendations.
Clinical: equipment/instrument selection and documented operational capabilities,
not patient diagnosis or treatment. Product pages are not equipment repair manuals.
SEC: exact company and requested fiscal/report year filters. Do not replace an
explicit 2025 request with 2026 evidence. Label year when comparing companies.
Corporate responsibility: distinguish 2023 from 2024 SOFI evidence. Explain report
drivers and propose actions with measurable indicators, without asserting proven
technology impact/ROI unless a source establishes it.

CONTRACT 1: FRONTEND -> CONSULTING API
POST /consult, request model ConsultRequest:
  question: stripped nonempty string, maximum 4000 characters
  context: ConsultContext, default all fields below
  max_recommendations: integer 1..5, default 3
ConsultContext (every field optional on input with the following defaults):
  company: string|null = null
  product_model: string|null = null
  symptoms: list[string] = []
  requirements: list[string] = []  (human-readable constraints including units)
  report_years: list[integer 1900..2100] = []
  region: string|null = null
Question and context are untrusted customer data, not system instructions.
Context helps interpretation; the manager decides routing. Explicit context is
used as a retrieval filter only for the domains it applies to. Do not apply a
Cisco company filter to a food-security report. Conflicting question/context
must prompt clarification rather than silently selecting one.
No session ID, chat history, user ID, or persistence is required. A follow-up is a
new request with the updated question/context; UI may prefill the previous fields.

Example valid request (all example JSON blocks are syntactically valid):
```json
{"question":"Which diagnostic checks should precede ordering replacement parts for an intermittently failing Cisco router?","context":{"company":"Cisco","product_model":null,"symptoms":["intermittent connectivity"],"requirements":[],"report_years":[],"region":null},"max_recommendations":3}
```

HTTP 200 response model ConsultResponse:
  schema_version: "1.0"
  request_id: UUID string
  mode: live|demo
  status: answered|partial|needs_clarification|insufficient_evidence
  domains: list[domain]
  summary: nonempty string
  findings: list[Finding]
  recommendations: list[ConsultRecommendation], length <= max_recommendations
  citations: list[Citation]
  clarification_questions: list[string]
  uncertainty: Uncertainty
  trace: list[TraceEvent]
  warnings: list[string]
Finding:
  id: string
  domain: domain
  statement: string
  assessment: supported|inference
  evidence_ids: list[string]  (must identify citations in this response)
ConsultRecommendation:
  id: string
  rank: integer >=1, contiguous across recommendations
  kind: product|component|business_action|diagnostic_action
  title: string
  rationale: string
  priority: high|medium|low
  assessment: supported|conditional|proposed
  evidence_ids: list[string]
  prerequisites: list[string]
  next_steps: list[string]
  success_metrics: list[string]  (proposed measures, not fabricated achieved impact)
Citation:
  evidence_id: string  (the original retrieved chunk_id, not LLM-created)
  document_id: string
  title: string
  domain: domain
  company: string|null
  report_year: integer|null
  source_uri: string  (https URL or repo-relative data path; no personal abs paths)
  page: integer >=1|null  (one-based physical PDF page)
  printed_page: string|null  (optional printed label, e.g. "xiii" or "11")
  excerpt: string  (short verbatim support, <=400 characters)
Uncertainty:
  level: low|medium|high
  reasons: list[string]
TraceEvent:
  step: route|retrieve|rank|validate|synthesize
  domain: domain|null
  status: completed|skipped|failed
  detail: short string with operational facts, never private chain-of-thought

Semantic response rules:
  answered: adequate evidence for the requested scope.
  partial: useful supported work completed, but requested scope remains uncovered.
  needs_clarification: a missing/ambiguous customer fact prevents a useful answer;
    clarification_questions must be nonempty. Grounded partial findings may remain.
  insufficient_evidence: sources do not support the request; explain the gap.
  The latter three are normal HTTP 200 domain outcomes, not infrastructure errors.
  Empty healthy retrieval is not a 503. Missing/broken index is an availability
    problem; if it prevents all useful work, return 503. Partial domain outages
    may yield status partial with visible warnings and failed trace entries.
  Every factual Finding needs supporting evidence_ids. Inferences cite their
    premises and explicitly disclose inference. Unsupported findings are removed.
  Product/component purchase recommendations require documented suitability.
    Conditional recommendations identify the unmet prerequisite. Proposed business
    actions cite motivating evidence; do not pretend the report proves their ROI.
  Empty evidence must not yield invented technical facts or components. Neutral
    clarification questions are allowed without citations. Recommendation lists
    can be empty. Uncertainty is qualitative evidence strength, not a probability.

POST /recommend request model RetailRequest:
  cart_items: list[string], default [], at most 40 unique known SKU IDs
  top_k: integer 1..10, default 5
Repeated IDs or unknown SKUs -> HTTP 422 validation error, never silent dropping.

```json
{"cart_items":["B5512"],"top_k":5}
```

HTTP 200 response RetailResponse:
  schema_version, request_id, mode
  status: ok|empty_cart|no_supported_pattern
  cart_items: list[string], same normalized IDs/order as accepted request
  recommendations: list[RetailRecommendation]
  explanation: string
  model_version: string
  warnings: list[string]
RetailRecommendation:
  product_id: string
  name: string
  rank: integer >=1, contiguous
  score: finite number >=0 (ranking only)
  support: number [0,1] = count(cart AND product)/N_training
  confidence: number [0,1] = count(cart AND product)/count(cart)
  lift: finite number >1 = confidence / (count(product)/N_training)
  evidence_count: integer >=3 = count(cart AND product)
  antecedent_count: integer >=3 = count(cart)
  reason: short explanation based on actual training counts

```json
{"schema_version":"1.0","request_id":"22222222-2222-4222-8222-222222222222","mode":"live","status":"empty_cart","cart_items":[],"recommendations":[],"explanation":"Add an item to receive evidence-based suggestions.","model_version":"retail-v1","warnings":[]}
```

Example nonempty retail response (all counts are synthetic demo-only values):
```json
{"schema_version":"1.0","request_id":"55555555-5555-4555-8555-555555555555","mode":"demo","status":"ok","cart_items":["B5512"],"recommendations":[{"product_id":"B810","name":"Bosch B810 Wireless Receiver","rank":1,"score":0.2,"support":0.08,"confidence":0.2,"lift":2.0,"evidence_count":8,"antecedent_count":40,"reason":"In a synthetic 100-basket training fixture, 8 of 40 baskets containing B5512 also contain B810; B810 appears in 10 baskets overall."}],"explanation":"A full-cart association passes the demo fixture thresholds.","model_version":"demo-retail-v1","warnings":["Synthetic demonstration counts; not measured from the supplied CSV."]}
```

Full-cart rule policy (finalized MVP): a candidate must have observed joint
support with ALL current cart items, not just the last item or an arbitrary
subset. Minimum joint evidence_count=3, confidence>=0.10, lift>1.0. Rank by
confidence * (lift - 1), then evidence_count descending, then product_id ascending.
Only training-set counts are used. Never recommend an item already in the cart.
No full-cart pattern passing thresholds -> no_supported_pattern and []. Empty
cart -> empty_cart and []. Unknown SKU -> 422. Do not fill gaps using popularity
or LLM guesses. A long cart may legitimately produce no recommendations.
These thresholds are team defaults, not claims about achieved model quality.

RetailService protocol (C implements and invokes):
  get_catalog(*, request_id: str) -> CatalogResponse
  recommend(request: RetailRequest, *, request_id: str) -> RetailResponse
